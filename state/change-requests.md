Formulas, `Decimal` only and never binary float: `tax_amount = ROUND_MONEY(sale_price × tax_rate_percent / 100)`, `margin = ROUND_MONEY(sale_price − total_cost − tax_amount)`, `margin_percent = ROUND_PERCENT(margin / sale_price × 100)`; the percentage is always divided by `100` (`6.00` = `6%`), money and percentage quanta are both `0.01` with `ROUND_HALF_UP`, only the final amount of each formula is rounded, and tax is deducted from gross revenue rather than added on top. Configured `0.00` produces tax `0.00`; a missing rate or missing sale price produces `null` and never a fabricated zero; margin is `null` when sale price, total cost, or tax is unavailable; margin percent is computed only when margin is available **and** sale price is greater than zero; zero sale price yields `partial` with margin percent `null`; negative margin and negative margin percent are valid and are **never clamped**. An invalid persisted rate is handled defensively: no calculation, no coercion, not treated as zero, raw value never exposed, estimate unavailable, non-blocking warning, no unhandled HTTP 500, and physical production not blocked. A missing `default_tax_rate` row and an invalid persisted value together form **`no valid configured tax-rate context`**: distinguishable through the warnings `tax_rate_missing` and `tax_rate_invalid` — the invalid case never also emits `tax_rate_missing` — but both return `tax_rate_percent = null` and `tax_rate_effective_at = null`, both leave tax, margin and margin percent unavailable, both map to the single `null/null` confirmation context, and **neither blocks physical production**; the invariant is that an absent or invalid tax-rate setting may make financial values unavailable but must not by itself block physical production. The raw invalid value never reaches a readiness DTO, a confirmation request, or a `ProductionBatch` snapshot, and confirmation never repairs, clears, rewrites, or audits it. Financial warnings are **non-blocking** and reuse the existing readiness mechanism and the exact existing `ProductionReadinessIssue` structure: `tax_rate_missing`, `sale_price_missing`, and `cost_data_missing` are **preserved and never renamed**, only `margin_percent_unavailable_zero_sale_price` and `tax_rate_invalid` are added, no aliases such as `tax_rate_unconfigured` / `sale_price_unavailable` / `total_cost_unavailable` are introduced, and no two warnings are emitted for one semantic condition; `can_produce` stays governed only by recipe/formula readiness, stock, lots, packaging, order lifecycle, and existing physical safety rules. Readiness mapping **reuses** the existing `estimated_cost`, `estimated_tax`, and `estimated_margin` fields and adds only `sale_price`, `tax_rate_percent`, `tax_rate_effective_at`, `estimated_margin_percent`, and `financial_estimate_status` (`available` / `partial` / `unavailable`); **`estimated_total_cost` is not authorized** and no duplicate alias is authorized. `C2-II` will add exactly two nullable `ProductionBatch` columns — `tax_rate_percent_snapshot` and `tax_rate_effective_at_snapshot` — with **no backfill**, reusing the existing `sale_price`, `total_cost`, `tax`, `margin`, and `margin_percent` fields and adding no duplicate monetary snapshot fields; it reads the setting inside the production transaction through a bounded read-only `connection`-aware extension of the C1 service, never through a second independent connection; confirmation carries **required-but-nullable** `expected_tax_rate_percent` and `expected_tax_rate_effective_at` declared without defaults, where **omission is not equivalent to explicit `null/null`** (omitted → HTTP 422 `tax_rate_context_required`; partial-null, malformed, non-canonical, out-of-range, or bad timestamp → HTTP 422 `invalid_tax_rate_context`); valid → changed valid, valid → missing, valid → invalid, missing → valid and invalid → valid all yield HTTP 409 `tax_rate_context_stale` and write nothing, while **missing ↔ invalid is deliberately not a conflict** because both produce the same financial result, and no third request field or generic context token is introduced; an accepted no-valid-rate confirmation persists null rate snapshots and null tax, margin and margin percent while completing physical production normally; and the two rate snapshots are exposed only in the confirmation response and `ProductionBatch` detail, not in the batch list or reports. Timestamps are exact: storage is `YYYY-MM-DD HH:MM:SS` UTC SQLite text (no `T`, no `Z`, no offset) for `AppSetting.updated_at` and the future `tax_rate_effective_at_snapshot`, while the API and confirmation context use `YYYY-MM-DDTHH:MM:SSZ`; local time, arbitrary offsets, fractional seconds, a space instead of `T`, and a missing `Z` are rejected with `422 invalid_tax_rate_context`, and the API never exposes the raw stored form. Reports read persisted snapshots **only**, never recalculate history with the current rate, and show old rows as unavailable rather than `0.00`.
